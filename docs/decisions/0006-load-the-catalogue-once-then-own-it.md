# 0006 — Load the catalogue once, then own it

**Status:** accepted
**Date:** 2026-08-30

This **amends [0005](0005-fndds-is-the-catalogue.md)**. It does not supersede it: FNDDS 2021-2023
is still the source, leucine is still estimated, and a nutrient correction still needs a citable
source. What changes is what happens to the table after the first load.

## Context

0005 was written expecting later FNDDS releases to be re-imported. That expectation is why it holds
corrections in a table apart from `Foods` — in its words, so that "re-importing a later FNDDS
release does not erase them".

`tools/CatalogueLoad` was built to match: it empties `Foods` and inserts the parsed file.

**That design costs a stable identity, and the cost is already visible in the loaded table.**
`Id` is `generated by default as identity`, and the sequence does not reset on delete. Measured on
2026-08-30: `Foods` holds 1 933 rows, and the alphabetically first milk, `Milk, NFS`, carries
`Id = 5347`. It carried `Id = 1` on the first load. Its `FdcId`, `2705384`, never moved.

While `Id` moves, nothing may hold one: not a URL, not a row in a user's log, not a foreign key.
Every feature after the catalogue needs to hold one.

Also measured the same day: all 1 933 rows carry an `FdcId`, and all 1 933 values are distinct.
No constraint requires that.

## Decision

**The catalogue was loaded once. `Foods` is Sated's table from here on.** Corrections are updates to
its rows, new foods are inserts into it, and nothing rewrites it wholesale.

**`CatalogueLoad` loses the ability to delete.** It refuses to run unless `Foods` is empty, so it
stays useful for building the catalogue on a fresh database and cannot destroy a grown one.

**`FdcId` stays, doing a different job.** It is no longer the key that matches old rows to new ones
across a re-import. It is provenance — the pointer that lets any stored number be checked against
its source, which is what 0005 requires of a correction — and it is the record of which USDA rows
are already held.

**`FdcId` gets a unique index, and stays nullable.** Foods that do not come from USDA have no
`FdcId`; PostgreSQL allows any number of nulls under a unique index, so those rows do not collide
with each other.

### What this changes in 0005

The corrections layer no longer exists to survive a re-import, because there is no re-import. It
keeps its other reason: the record of what was changed, from what value to what value, on what
source. So does the tool 0005 requires alongside it — the one that reports how many letters the
corrections move. That number was the guard, and the guard is still needed.

## Alternatives considered

**Keep wipe-and-reload, and re-apply corrections after each load.** This is what 0005 assumed, and
it buys one real thing: USDA's own later corrections arrive for free. It loses on two counts. The
renumbering above makes every food unreferenceable, which blocks the whole product and not just a
feature. And 0005 already decided that USDA values are not taken unreviewed — so the free
corrections would each need reading anyway, which is the expensive half of importing them by hand.

**Make `FdcId` the primary key.** It removes the renumbering problem outright and needs none of
this. It fails on the foods that are not from USDA: they have no `FdcId`, so the key would have to
be nullable, and a primary key cannot be. It would also hand Sated's identity to an external
provider's numbering, which then has to stay valid for the life of the product.

**Delete `CatalogueLoad`.** It has done its job and git holds it. Rejected because rebuilding the
catalogue on an empty database — a new machine, a fresh volume, a restored environment — is a thing
that will be needed, and a tool that can only fill an empty table is safe to keep around.

## Consequences

- **`Id` is stable for the life of a row.** This is what makes `GET /api/foods/{id}` safe, and what
  lets a food be referenced from anywhere else in the schema.
- **The catalogue ages, and nothing refreshes it.** FNDDS 2021-2023 is a snapshot. 0005 accepted
  that for nutrient values; this makes it true for the whole table, including foods USDA adds later.
- **Taking foods from a later FNDDS release becomes a different job from loading:** read the new
  file, insert only the `FdcId`s not already held. It is not built, and it is not needed until a
  release lands.
- **The letter cutoffs are percentiles of the FNDDS population.** Foods added by hand change that
  population, and nothing fails when it stops matching. This is the same question as **D2**, now
  triggered by our own growth rather than by a USDA release.
- **A duplicate USDA food can no longer be inserted by accident**, and the failure is loud: the
  database rejects the insert instead of the duplicate being found later in a report.
- **Emptying `Foods` is now a deliberate act, written by hand in psql.** That is the point.
- **A food added by hand has to reuse a category string the catalogue already carries.** `Category`
  is read by the twenty-one category rules and by the per-category leucine shares in
  `ProteinCompleteness`, both keyed on FNDDS's own wording. A food filed under an invented category
  matches no rule and nothing fails — it simply scores as though those rules did not exist. The
  seventy-one strings in `Sated.Parsing/CatalogueCategories.cs` are the set to pick from. Nothing
  in the schema enforces this yet.
- **Names will be translated; categories will not.** `Description` is the field a Romanian or any
  other name replaces. `Category` cannot be, for the reason above and as
  [0005](0005-fndds-is-the-catalogue.md) already records. Translating the description is also what
  makes `FdcId` load-bearing: once the English text is gone, it is the only thing still pointing at
  the row the numbers came from.
